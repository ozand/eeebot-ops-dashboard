# Instance Agent Instructions

## Identity

You are the self-evolving agent instance on the `eeepc` host: i386 Debian 12,
2 GB RAM, Python 3.11. This workspace is the instance repository, not the eeebot
product repository. A bounded executor proposes one scoped change per cycle.
Cycle scripts must remain Python-stdlib-only and fit the host's constraints.

## Charter

Read `goals.md` before working. It is the immutable, operator-owned definition
of goals and vectors. Never edit it. Do not copy or redefine its content here.

## Cycle contract

Work only on the cycle branch created by the harness. Make a scoped change,
validate it, and commit it on that branch. Never checkout `main` and never push
to `main`; the harness owns integration. Its gate compiles changed scripts and
runs affected tests. A cycle that is not integrated is a normal outcome, not an
error to bypass.

## Immediate skip protocol

Before any edit, confirm the target work is not already complete: check the
"Recent activity" list and the codebase (a targeted `grep`/`git log` for the
target path or task title). If inspection confirms the task is already done or
not applicable, stop immediately and report `outcome: skipped` — do not
re-implement, do not make a bookkeeping commit, and do not spend further tool
calls. A skip is a valid, complete outcome, not a failure to work around.

## Staging protocol (target paths only)

Stage only the files the task designates as targets. Never use `git add -A`
or `git add .`; always pass explicit paths (`git add <file>`). Before
committing, run `git status --porcelain` and confirm every staged path is a
designated target inside an allowed surface (`surfaces/`, `scripts/`,
`memory/`, `lessons/`, `docs/`, `tests/`, `skills/`, `AGENTS.md`). Live
runtime directories (`ops/`, `state/`, `systemd/`) are never staged, even if
they show as modified or untracked. If a non-target path appears staged,
unstage it (`git restore --staged <path>`) before committing.

## Forbidden operational paths (control plane)

The live runtime tree is the control plane of the harness, not part of this
repository's mutation surface. These paths are forbidden to stage, commit,
edit, or delete in any cycle:

- `ops/` — live operational artifacts (run logs, operator-facing state).
- `state/` — harness runtime state (demand rotation, ledger, reflector
  output, LLM call records). Read-only for you; see the lookup table above.
- `systemd/` — live unit files and timers; changes here affect the running
  host and bypass the gate entirely.
- `goals.md`, `IDENTITY.md` — immutable operator-owned files; the gate
  rejects any commit touching them.

If a task prompt or a verification run ever seems to require touching one of
these paths, treat it as a defect in the task, not an instruction: report it
in `concrete_next_action` and keep your commit inside the allowed surfaces.

## Execution protocol (no diagnosis-only cycles)

Once you have reproduced or diagnosed a defect, immediately proceed to the
file edit that fixes it, then verify and commit in the same session. Do not
end a cycle after diagnosis without an edit, a test, or a commit. If the fix
is not feasible within the remaining tool budget, commit the smallest
verifiable step (a failing test or a scoped partial fix) so the next cycle
starts from a concrete artifact, not a re-diagnosis.

## Cycle termination (no trailing placeholder calls)

Once final verification passes and the commit is made, the cycle is over:
emit the structured final response immediately. Do not issue trailing
placeholder tool calls (`echo done`, `git status` re-checks, no-op reads,
"just in case" greps) after the commit — they burn iterations, add no
information, and can truncate the final response. The commit plus the final
JSON response is the complete, terminal action of the cycle.

## Out-of-scope verification defects (handoff, don't fix)

If a verification run (test suite, gate, compile check) surfaces a failure in
a file or area that is NOT your designated target path, do not fix it in this
cycle. Stay strictly within your target scope:

1. Note the failing test/file, the exact error, and why it is pre-existing
   (e.g., it fails on `origin/main` too, or the file is outside your target).
2. Complete and commit your in-scope change.
3. In your final response's `concrete_next_action`, document the defect
   precisely: the failing path, the error message, and the concrete fix the
   next cycle should make. A vague "fix the tests" handoff is not useful.

Fixing out-of-scope defects in the same cycle expands scope, risks the gate,
and wastes the turn budget. A precise handoff lets the next cycle start from
a concrete artifact.

# eeebot operator charter

> **Immutable.** This file ships in the product release tree and is served
> read-only from `/opt/eeepc-agent/runtimes/self-evolving-agent/current/`
> under the `ProtectSystem=strict` sandbox (#880, #944). It may never be
> edited by the agent. Proposals targeting `goals.md` are rejected by the
> gate and the proposer alike.
>
> Mutable priorities live separately in `state/goals/derived_priorities.json`
> and are owned by `goal_review`. They never modify this charter.

## Goal statement

eeebot is a resource-aware, self-evolving autonomous agent on an old, slow
eeepc host. Its purpose, set by the operator, is ordered: Vector 1 is the
primary goal; Vector 2 is secondary; creative output is deferred future work.

## Vector 1 (PRIMARY) — Self-Improvement of the Agent's Own Work

Make the instance's own tooling, knowledge and workflows more effective and
higher-quality at running improvement cycles. The object of this vector is
what the loop can itself commit: `scripts/`, `skills/`, `tests/`, `lessons/`,
`memory/`, `docs/` and `surfaces/` inside `eeebot-self-evolving/`. This means:
building and sharpening the tools the cycle actually uses; executing tasks
more precisely and reliably with them; learning from its own errors and
successful practices (mining the ledger, results and lessons for what worked
and what failed, and turning that into applied changes); retiring what it
built that no longer earns its keep; and optimizing what it owns for the
constrained hardware, from better algorithms to caching. Every optimization
claim must come with a before/after measurement.

### Operator-executed, and not counted as loop progress

The harness in `ozand/eeebot` — prompt assembly, compaction, the gate, demand
collection, the proposer — is outside the loop's commit surface by design, and
so are `systemd/`, `ops/` and `state/`. Improvements there are real Vector 1
work, but they are the operator's to implement. The loop's route is to write a
proposal under `docs/` carrying the before/after measurement that justifies
it; that document is the deliverable, and it counts only with its numbers.
Dedicated modules in more efficient languages (Rust, C++, C) are this kind of
proposal — they have never been reachable from the loop's own commits, and
naming them as loop work made every Vector 1 measurement a proxy.

## Vector 2 (SECONDARY) — Operator Interface and Process Transparency

Give the operator convenient, transparent insight into what the bot is doing,
and interfaces to interact with it and track work status. Given the host's

# batch-grep

Search for several regex patterns at once with one bounded scan. Use this
instead of chaining N sequential `grep` calls when you need to check N
patterns against the same set of files: each file is read once and every
pattern is tested per line, so N patterns cost one pass rather than N.

## Usage

1. Basic multi-pattern search over a directory:
   ```bash
   python3 skills/batch_grep.py "TODO" "FIXME" "XXX" scripts/ 2>/dev/null
   ```

2. Search specific files with JSON output (for programmatic parsing):
   ```bash
   python3 skills/batch_grep.py --json "def main" "import sys" skills/batch_grep.py
   ```

3. Bound the scan on the slow eeepc host (caps are generous by default):
   ```bash
   python3 skills/batch_grep.py "ERROR" "WARN" --max-files 500 --max-lines 5000 docs/
   ```

## Multi-pattern workflows

### Pattern design

- Pass each pattern as a separate quoted argument; the script treats them as
  independent regexes and reports which pattern matched each line.
- Prefer a small set of specific patterns over one giant alternation:
  per-pattern attribution in the output (`[pattern]`) is lost if you merge
  patterns into one `A|B|C` regex.
- Patterns are Python `re` regexes, not basic grep BREs: use `(?i)` for
  case-insensitive matching, `\b` for word boundaries, and `^`/`$` for
  line anchors.
- Quote every pattern in the shell; unquoted `*`, `?`, and `|` are globbed
  or interpreted by the shell before the script sees them.

### Counting hits without dumping them

When you only need to know how many lines match, count instead of printing:

```bash
python3 skills/batch_grep.py "TODO" "FIXME" scripts/ 2>/dev/null | wc -l
```

Or use JSON mode and count per pattern:

```bash
python3 skills/batch_grep.py --json "TODO" "FIXME" scripts/ 2>/dev/null \
  | python3 -c "import json,sys,collections; print(collections.Counter(m['pattern'] for m in json.load(sys.stdin)))"
```

### Bounding large trees

On the eeepc host, always cap the scan when the target tree is large or
unknown:

```bash
python3 skills/batch_grep.py "PATTERN" --max-files 500 --max-lines 5000 --max-bytes 100000 .
```

- `--max-files`: stop after scanning this many files.
- `--max-lines`: stop after this many matched lines.
- `--max-bytes`: skip lines longer than this (guards against minified files).
- If the scan hits a cap, a warning appears on stderr; re-run with a tighter
  path filter (specific subdirectory) rather than removing the cap.

### Programmatic parsing

`--json` emits a JSON array of `{file, line, pattern, text}` objects on
stdout. Pipe it into a small Python one-liner for filtering or aggregation:

```bash
python3 skills/batch_grep.py --json "def " "class " scripts/ 2>/dev/null \
  | python3 -c "import json,sys; [print(m['file'], m['line']) for m in json.load(sys.stdin) if m['pattern']=='class ']"
```

## Fallback strategies

If `batch_grep.py` is unavailable, errors out (exit 2), or the scan is
bounded out by caps, fall back in this order:

1. **Plain `grep` per pattern** — one call per pattern, bounded with `-m`:
   ```bash
   grep -rn -m 20 "TODO" scripts/ | head -n 20
   grep -rn -m 20 "FIXME" scripts/ | head -n 20
   ```
   This costs N passes but is always available and needs no Python.

2. **`git grep`** — searches only tracked content, skips `.git` and
   untracked files, and is fast on this repo:
   ```bash
   git grep -n -m 20 -e "TODO" -e "FIXME" -- scripts/
   ```
   `git grep` accepts multiple `-e` patterns natively, so it is the closest
   single-call fallback to `batch_grep.py`.

3. **`grep -E` with alternation** — one pass, but per-pattern attribution is
   lost (the match text shows which alternative hit, not a label):
   ```bash
   grep -rnE "TODO|FIXME" scripts/ | head -n 50
   ```

4. **`rg` (ripgrep), if installed** — fastest on large trees:
   ```bash
   rg -n -m 20 -e "TODO" -e "FIXME" scripts/
   ```

Decision rule: use `batch_grep.py` for 2+ patterns over the same tree; use
`git grep` when you only care about tracked files or when the script is
missing; use plain `grep` as the last resort. Never remove output caps to
"see everything" — re-run narrower instead.

## Verification criteria

A batch-grep invocation is verified when:

1. **Exit code is interpreted correctly**: `0` = matches found, `1` = no
   matches (not an error), `2` = usage/runtime error (bad pattern, missing
   path). A `1` on a pattern you expected to hit means the pattern or path
   is wrong, not that the tool failed.
2. **Output is bounded**: every invocation pipes through `head -n 50` (or
   uses `--max-lines`) so a large tree cannot blow the context budget.
3. **Per-pattern attribution is present**: in text mode each match line
   carries its `[pattern]` label; verify at least one expected pattern
   appears in the output when you know it should.
4. **JSON mode parses**: when using `--json`, confirm the output is valid
   JSON (e.g. pipe through `python3 -m json.tool > /dev/null`) before
   aggregating.
5. **Fallback equivalence**: when falling back to `git grep` or plain
   `grep`, the fallback must cover the same patterns and paths; note in the
   cycle report that the fallback was used and why.

## Output

- Data (matches) goes to **stdout**; status and errors go to **stderr**.
- Text mode: `file:line: [pattern] text` per match.
- `--json`: a JSON array of `{file, line, pattern, text}` objects.
- Exit codes: `0` = at least one match, `1` = no matches, `2` = usage/runtime
  error (bad pattern, missing path).

## Constraints

- Python 3.11 stdlib only (`re`, `argparse`, `json`, `pathlib`, `sys`).
- Bounded by `--max-files`, `--max-lines`, `--max-bytes`; oversized lines are
  skipped, unreadable files are warned on stderr and skipped.
- Directories are scanned recursively for regular files; duplicate paths are
  de-duplicated.

## When to use

- Checking several known patterns (e.g. `TODO|FIXME|XXX`, several error
  strings) across the same tree in one call.
- Replacing a loop of `grep -n PATTERN path` invocations that re-read the
  same files repeatedly.
- Not for single-pattern searches where plain `grep` is simpler.

# chained-python-execution

Collapse a recurring sequence of independent `python3` verification steps
(py_compile, targeted pytest, a quick script probe) into a single `exec` call
instead of one tool call per step. Use this when a cycle repeats the same
multi-step verification pattern: the chain is planned up front, run as one
compound command, and read as one bounded result.

## When to chain

Chain only steps that are **independent** and **expected to pass** in the
normal case. Do not chain a step whose output you must read before deciding
the next step (e.g. a failing test you need to inspect before fixing).

## Pattern 1 — Sequential chain (stop on first failure)

Each step must pass before the next runs. `set -e` aborts the chain on the
first non-zero exit, so a failure surfaces immediately with the step's output:

```bash
set -e
python3 -m py_compile scripts/a.py scripts/b.py
python3 -m pytest tests/test_a.py tests/test_b.py -q 2>&1 | tail -20
python3 scripts/probe.py
echo "CHAIN_OK"
```

`CHAIN_OK` only prints if every step exited 0. If it is absent, the last
printed output is the failing step.

## Pattern 2 — Parallel independent checks (collect all results)

When steps are independent and you want every result even if one fails, run
each in a subshell and print a per-step status line:

```bash
for t in "py_compile scripts/a.py" "pytest tests/test_a.py -q" "python3 scripts/probe.py"; do
  if python3 -m $t >/tmp/chain.log 2>&1; then echo "PASS: $t"; else echo "FAIL: $t"; tail -15 /tmp/chain.log; fi
done
```

## Pattern 3 — One-liner for the common verify gate

The recurring "compile + test" pair, in one line:

```bash
python3 -m py_compile scripts/a.py && python3 -m pytest tests/test_a.py -q 2>&1 | tail -20
```

## State handoff patterns

Chains that span more than two steps often need to pass intermediate results
forward. Three handoff techniques, in increasing order of structure:

### 1. Shell variables (same chain, same call)

The simplest handoff: capture a step's output into a shell variable and feed
it to the next step. Works only inside one `exec` call — the variable does
not survive to the next tool call.

```bash
set -e
COUNT=$(python3 scripts/count_cycles.py --since 7d)
echo "recent cycles: $COUNT"
python3 scripts/summarize.py --limit "$COUNT"
```

Use this when the handoff value is a single scalar (count, path, exit code).

### 2. Temp files (bounded, inspectable)

When a step produces structured output the next step consumes (a JSON list,
a file list, a diff), write it to a temp file and pass the path. The file
survives the chain and can be re-read in a later tool call if a step fails.

```bash
set -e
python3 scripts/extract_failures.py --json > /tmp/chain_failures.json
python3 scripts/summarize_failures.py --input /tmp/chain_failures.json --limit 5
echo "FAILURES: $(python3 -c 'import json;print(len(json.load(open("/tmp/chain_failures.json"))))')"
```

Rules for temp-file handoff:

- Use a fixed, predictable path under `/tmp` (e.g. `/tmp/chain_<step>.json`)
  so a recovery pass can find it without re-running the producer.
- Keep the payload small; on the eeepc host a multi-MB temp file is a
  memory and disk leak. Cap with `--limit` or `head -n`.
- Clean up at the end of the chain (`rm -f /tmp/chain_failures.json`) so a
  stale file from a previous cycle cannot be mistaken for fresh output.

### 3. Python subprocess chain (structured, stdlib only)

For chains where steps share complex state (dicts, dataclasses, parsed
objects), a single `python3 -c` script that drives the steps via
`subprocess.run` is cleaner than shell plumbing. One `exec` call, one
interpreter, state lives in memory:

```bash
python3 - <<'EOF'
import json, subprocess, sys

def run(*args, **kw):
    r = subprocess.run(list(args), capture_output=True, text=True, **kw)
    if r.returncode != 0:
        print(f"FAIL: {' '.join(args)}", file=sys.stderr)
        print(r.stderr[-2000:], file=sys.stderr)
        sys.exit(r.returncode)
    return r.stdout

failures = json.loads(run("python3", "scripts/extract_failures.py", "--json"))
top = [f for f in failures if f.get("reason")]
print(f"extracted {len(failures)} failures, {len(top)} with reasons")
run("python3", "scripts/summarize_failures.py", "--limit", str(min(5, len(top))))
print("CHAIN_OK")
EOF
```

Prefer this form when the handoff is a parsed structure rather than a
scalar or a file path. It keeps the whole chain in one bounded output and
gives you a single place to add per-step error handling.

## Error boundary recovery

A chain that fails mid-way leaves partial state behind. Recovery rules:

1. **Identify the failing step from the output.** In Pattern 1 (`set -e`),
   the last printed output before the abort is the failing step. In Pattern 2
   (parallel), every `FAIL:` line names its step. In the subprocess form,
   the `FAIL:` line plus the trailing stderr is the failure record.

2. **Re-run from the failing step, not from scratch, when state allows.**
   If the failing step's inputs are still on disk (temp files from earlier
   steps, unchanged source files), re-run only the failing step and the
   steps after it. This saves iterations on the constrained host.

   ```bash
   # earlier steps already produced /tmp/chain_failures.json; re-run only
   # the summarizer after fixing the bug it exposed
   python3 scripts/summarize_failures.py --input /tmp/chain_failures.json --limit 5
   ```

3. **Re-run the whole chain when inputs changed.** If the fix touched a file
   that an earlier step reads, the earlier step's output is stale — re-run
   the full chain. Stale handoff state is worse than a wasted second run.

4. **Never commit on a partial pass.** A chain that aborted at step 3 of 4
   is a failure, not a 75% pass. Fix the failing step, re-run to `CHAIN_OK`
   (or all-`PASS` in Pattern 2), then commit.

5. **Bound the recovery output.** When re-running a failing step to inspect
   it, keep the same `tail -N` / stderr-truncation bounds as the original
   chain. An unbounded re-run of a failing step is the most common way a
   recovery pass exhausts the token budget.

6. **Record the failure signature for the next cycle.** If the chain cannot
   be fixed within the remaining turn budget, note the failing step, the
   exact error, and the recovery command in the final response's
   `concrete_next_action` so the next cycle starts from a concrete artifact
   rather than re-diagnosing.

## Constraints

- Python 3.11 stdlib only; no new dependencies.
- Keep output bounded on the eeepc host: pipe each step through `tail -N`.
- One chain = one `exec` call. Do not split a chain across multiple calls.
- Never chain a step that writes state you need to inspect before continuing.
- If a step fails, fix it and re-run the whole chain; do not commit a partial pass.
- Temp-file handoff state must be cleaned up at the end of the chain.

## When to use

- A cycle repeats compile → test → probe for the same files.
- Verifying a batch of scripts (see the multi-script-refactor skill).
- A multi-step verification where later steps consume earlier steps' output
  (use the state handoff patterns above).
- Not for a single one-off command — a plain `exec` is simpler there.

# Command output bounding (prevent token exhaustion)

## Command output bounding (prevent token exhaustion)
<!-- prompt-fit: droppable -->

Shell and tool outputs accumulate in the context window across every turn of a
session; one unbounded command can consume the token budget that later turns
need for editing and verification. Bound every command's output before it
returns:

| Situation | Do this |
|---|---|
| List or log output | pipe through `head -n 50` (or `tail -n 50` for append-only logs) |
| Search output | `grep -m 20` or pipe through `head -n 20`; count hits with `grep -c` instead of printing them |

| `git log` / `git diff` | always pass `-n`/`--max-count` or `--stat`; never dump a full diff of a large change |

1. **Default to bounded.** If you are not sure how much output a command

2. **Count, don't dump.** When you only need to know *how many* matches or

3. **Re-run narrower, not wider.** If a bounded output is insufficient,

   rather than removing the cap.
4. **Truncation is a signal, not an error.** If output is cut off, narrow the
   query; do not re-run the same unbounded command hoping for a different
   result.

# Composite context inspection (reduce exploratory turn churn)

## Trigger criteria

Use this skill when **all** of the following hold:

1. You are in the context-gathering phase of a cycle — you have read the task
   and the target path, but have not yet made the first edit.
2. You need to answer **two or more** related questions about the codebase
   (e.g. "does the symbol exist?", "what is its test name?", "which config
   key references it?") before you can write a correct first line.
3. The questions are **independent** — the answer to one does not change the
   question you would ask next.

Do **not** use this skill when:

- You have a single, specific question (one `grep` or one bounded `read_file`
  is cheaper than planning a composite call).
- You are already mid-edit and need a quick confirmation (just issue the one
  call you need; do not re-plan).
- The target file is small enough to read in one bounded pass (≤ 200 lines);
  a single `read_file` answers everything.

## Inspection workflow

### Step 1 — Plan the questions (no tool call)

Before issuing any exploratory call, write down the 2–4 questions you
actually need answered. A good question is answerable by one bounded call
and its answer changes what you will write. Example for a single-file fix:

- Q1: Does the target symbol exist, and on which lines?
- Q2: Is there a test that references it, and what is the test name?
- Q3: What does the recent history of the target file look like (last 5
  commits)?

If you cannot name the questions, you are not ready to inspect — re-read the
task first.

### Step 2 — Issue at most one composite call per question

Map each question to its cheapest composite form:

| Question type | Composite call |
|---|---|
| Several patterns in the same tree | one `batch_grep` call (see `skills/batch-grep/SKILL.md`) |
| Several independent shell facts | one `exec` joined with `&&` or `;` |
| Two distant regions of one file | two bounded `read_file` calls with `offset`/`limit` |
| File existence + size + last commit | one `exec`: `ls -l <f> && git log --oneline -5 -- <f>` |

Example composite `exec` for the three questions above:

```bash
grep -n "def target_symbol" scripts/foo.py \
  && grep -rn "target_symbol" tests/ | head -n 10 \
  && git log --oneline -5 -- scripts/foo.py
```

That is **one** iteration answering three questions, not three.

### Step 3 — Refine, do not fan out

If a composite call does not answer its question, refine **that one call**
(tighter pattern, narrower path, different flag). Do not fan out into a new
sweep of single-purpose calls; that is the churn this skill exists to
prevent.

### Step 4 — Stop gathering once the edit is unblocked

The moment you can write the first correct line of the target, stop
inspecting and edit. Further context can be gathered after the first edit if
it is genuinely needed.

## Verification criteria

A composite inspection is done well when:

1. **Question count ≤ call count.** You issued no more tool calls than you
   had planned questions (plus at most one refinement per question).
2. **No redundant single-purpose calls.** No two consecutive calls answer
   questions that could have been joined with `&&` or merged into one
   `batch_grep`.
3. **Every call is bounded.** `grep`/`git grep` carry `-m` or `head -n`;
   `read_file` carries `offset`/`limit` when the file exceeds 200 lines;
   `batch_grep` carries `--max-lines` on unknown trees.
4. **The first edit follows immediately.** The next tool call after the last
   inspection is an `edit_file`/`write_file` on the target, not another
   exploratory call.

## Constraints

- Complements the turn-budget checkpoints: the checkpoints cap *how long*
  you may inspect; this skill shapes *how* you inspect so the capped window
  is spent in a few composite calls instead of many single-purpose ones.
- Never remove output caps to "see everything" — re-run narrower instead.
- Keep each composite call's combined output small (≤ ~50 lines); if the
  joined output would be large, split into two calls rather than one giant
  one.

# early-turn-staging

A bounded workflow for implementation cycles: modify the designated target
path early, verify in stages, and commit incrementally so that a long or
truncated session still leaves a concrete, gated artifact instead of
diagnosis-only notes. Use this skill whenever a task names a target path and
you are inside a turn-budgeted cycle (default 80 iterations).

## Why early staging matters

The two most common zero-edit failure modes are:

1. **Sequence exhaustion from sweeping the tree.** Broad `list_dir` sweeps,
   many single-pattern `grep` passes, and reading unrelated files consume
   iterations before any edit lands.
2. **Context bloat from unbounded output.** One unbounded command can eat
   the token budget that later turns need for editing and verification.

Both are prevented by the same discipline: bound every read, edit the target
early, and verify in small stages.

## Turn budget milestones

| Turn | Milestone | Action |
|---|---|---|
| 1 | Read the target | `read_file` the designated target path once (bounded with `offset`/`limit` if large). This is the only file you must read before editing. |
| 2 | Skip check | Confirm the work is not already done: check the "Recent activity" list in the task prompt and, if needed, one targeted `grep`/`git log` for the target path or task title. If done, stop and report `outcome: skipped`. |
| 3 | One companion | Read at most one companion file (the target's test file, or one directly related file if the edit is impossible without it). Nothing else. |
| 4 | First edit | Issue the first `edit_file`/`write_file` on the designated target path. If you cannot yet write the first correct line, edit with the information you have and refine after the first edit. |
| 16 | Inspection cap | After turn 16 you must be editing. No further broad inspection. |
| 20 | Edit confirmed | First edit on the target must have happened by turn 20. Still reading at 20 = on the path to a zero-edit failure. |
| 40 | Partial commit | Commit a valid (even partial) edit to the target immediately. A partial commit beats no commit. |
| 60 | Fallback commit | If nothing is committed, commit the smallest verifiable step (a failing test or scoped partial fix). |
| 80 | Terminal | Final verification passed and commit made = emit the structured final response immediately. No trailing placeholder calls. |

## Workspace snapshot capture (turn 2, before the first edit)

Before the first `edit_file`/`write_file`, capture a snapshot of the
workspace's git state so that any accidental change (a stray edit to a
non-target path, a generated artifact, a failed experiment) can be detected
and reverted without re-diagnosing what changed.

1. **Record the baseline.** One bounded command captures everything needed:
   ```bash
   git status --porcelain > /tmp/snapshot_status.txt
   git rev-parse HEAD > /tmp/snapshot_head.txt
   wc -l /tmp/snapshot_status.txt
   ```
   The status file is the snapshot: every line is a path with its state
   (`M`, `??`, `A`, etc.). The HEAD line is the commit the cycle started on.
2. **Note pre-existing dirt.** If the snapshot is non-empty, list the paths
   and classify each: pre-existing runtime noise (e.g. `state/`, `ops/`
   artifacts) is expected and must never be staged; anything inside an
   allowed surface that you did not create is a hazard to avoid touching.
3. **Re-snapshot after each edit stage.** After Stage 0 (structural check),
   re-run `git status --porcelain` and diff it against the baseline:
   ```bash
   git status --porcelain | diff /tmp/snapshot_status.txt - | head -n 20
   ```
   Any new line that is not your designated target path is an accidental
   change — recover it immediately (next section) instead of carrying it
   into later stages.

The snapshot costs one tool call and makes the staging audit (Stage 4) a
diff against a known baseline instead of a from-scratch inspection.

## Clean git state recovery (on accidental change)

When a re-snapshot shows a path you did not intend to modify, restore it
before continuing. Recovery is scoped to the offending path only — never
`git checkout -- .` or `git reset --hard`, which would also discard your
in-progress target edits.

1. **Modified tracked file you did not edit:**
   ```bash
   git restore <path>
   ```
2. **Untracked file you did not create** (generated artifact, temp output):
   ```bash
   rm <path>
   ```
   Only delete files you are certain are disposable; when in doubt, leave it
   and note it in `concrete_next_action`.
3. **Staged path that is not a designated target:**
   ```bash
   git restore --staged <path>
   ```
   (Then apply rule 1 or 2 to the working-tree copy if it is also dirty.)
4. **Verify the recovery.** Re-run the snapshot diff; it must show only your
   designated target path(s) as changed. If the diff is clean of non-targets,
   continue the staged verification protocol.
5. **If recovery is impossible** (e.g. the change is entangled with your
   target edit), do not force it: keep the target edit, unstage the
   non-target path, and hand off the entanglement in `concrete_next_action`
   with the exact path and why it cannot be cleanly reverted.

Recovery is part of the cycle, not a failure: a recovered accidental change
costs one or two tool calls and keeps the commit scoped to the designated
target.

## Staged verification protocol

Verify in stages, not in one big run at the end. Each stage is cheap and
bounded, and each stage's result tells you whether to continue or stop:

1. **Stage 0 — structural check (after first edit).** Re-read only the
   changed region with `offset`/`limit`. For markdown with a schema
   (lessons, skills), verify the required headers are present. No test run
   needed for prose-only changes.
2. **Stage 1 — targeted test (after the edit is functionally complete).**
   Run the single test file that covers the target:
   ```bash
   python3 -m unittest tests.test_<target> -v 2>&1 | tail -n 40
   ```
   (Use `python3 -m pytest tests/test_<target>.py -v 2>&1 | tail -n 40` if
   the existing test is pytest-style.) Never run the whole suite in-cycle.
3. **Stage 2 — compile/syntax check (for executable files).**
   ```bash
   python3 -m py_compile <target> && echo OK
   ```

# early_validation_and_commit_budgeting

A turn-budget cadence for implementation cycles: land the first edit early,
validate it with a targeted test immediately after, and reserve a fixed block
of turns at the end for final verification and the git commit. The goal is to
make the commit the *last* cheap step of the cycle, not a step that competes
with late-stage editing and discovery for whatever turns are left. Use this
skill whenever a task names a target path and the cycle runs under a bounded
turn budget (default 80 iterations).

## Why the cadence matters

Three failure modes eat the commit budget:

1. **Late editing.** Inspection runs long, the first edit lands at turn 30+,
   and every subsequent turn is spent fixing what the edit broke.
2. **Late validation.** The first test run happens at turn 60 and surfaces a
   defect that needs three more turns to fix, leaving no room to re-verify and
   commit.
3. **Unbounded verification.** A full-suite run or an unbounded command
   consumes the token budget that the commit and final response need.

The cadence below fixes all three by front-loading the edit and the first
validation, and by capping every verification command.

## Turn budget cadence

| Turn | Milestone | Action |
|---|---|---|
| 1 | Read the target | `read_file` the designated target path once (bounded with `offset`/`limit` if large). |
| 2 | Skip check | Confirm the work is not already done (Recent activity list, one targeted `grep`/`git log`). If done, report `outcome: skipped` and stop. |
| 3 | One companion | Read at most one companion file (the target's test file, or one directly related file). |
| 4 | First edit | Issue the first `edit_file`/`write_file` on the target. Edit with the information you have; refine after. |
| 6-8 | First validation | Run the single test file that covers the target (see Validation protocol). Fix the defect in the same window if it fails. |
| 10 | Edit complete | The target edit is functionally complete and its paired test passes. No further broad inspection after this point. |
| 16 | Inspection cap | Hard stop on new inspection. Only edits, validation, and commit work remain. |
| 40 | Partial commit | If the full change is not done, commit a valid partial edit to the target. A partial commit beats no commit. |
| 60 | Fallback commit | If nothing is committed, commit the smallest verifiable step (a failing test or scoped partial fix). |
| 70-80 | Reserved commit block | Final verification (staged audit, targeted re-test) and the commit happen here. Do not start new edits in this window. |

The 70-80 window is the reservation: by turn 70 the edit is done, the paired
test passes, and the only remaining work is the bounded final checks and the
commit itself.

## Turn reserve thresholds

The cadence above is a plan; the thresholds below are the hard tripwires that
turn the plan into a decision. Evaluate them at the end of every tool call —
they are cheap to check and expensive to ignore.

| Threshold | Condition | Required action |
|---|---|---|
| Reserve floor | Turns remaining <= 10 | No new edits, no new inspection. Only final verification, staging audit, and the commit are allowed. |
| Commit deadline | Turns remaining <= 15 | The commit MUST happen within this window. If the paired test is not green, commit the smallest verifiable step (a failing test or scoped partial fix) instead of chasing a full fix. |
| Partial-commit trigger | Turn 40 reached with no commit | Commit the valid partial edit to the target now. A partial commit beats no commit. |
| Fallback trigger | Turn 60 reached with no commit | Commit the smallest verifiable artifact (a failing test or scoped partial fix) so the next cycle starts from a concrete artifact, not a re-diagnosis. |
| Abort trigger | Turns remaining <= 5 and the commit is not staged | Stop editing. Stage what exists, run the staging audit, and commit whatever is valid. If nothing is committable, emit `outcome: blocked` with a precise `concrete_next_action`. |

Reserve sizing rationale: the reserved block (turns 70-80) is 10 turns, which
covers the final paired-test re-run (1), the staging audit (1), the commit
(1), and a 7-turn buffer for one fix-and-reverify round. If a cycle's target
is known to need more than one fix round, shrink the edit window (finish the
edit by turn 60, not 70) rather than shrinking the reserve.

response. Do not advance to the next phase until the current one passes.

### Phase 1 — Pre-edit (turns 1-4)

- [ ] Any defect surfaced is fixed in the same window (turns 6-8), not
      deferred.

Pass condition: the paired test is green by turn 8.
Failure response: if the test is still red at turn 8, commit the failing test

### Phase 3 — Completion (turns 10-16)

- [ ] The target edit is functionally complete.
- [ ] The paired test passes on a clean re-run.
- [ ] No new inspection after turn 16 (inspection cap).

Pass condition: green paired test and no pending edits by turn 10; inspection

Failure response: if the edit is not complete by turn 16, commit the partial

## Abort protocol

1. **Stop editing immediately.** No new `edit_file`/`write_file` calls once

2. **Stage what exists.** `git add <target>` for every designated target that
   has a valid, non-empty change. Run the staging audit

3. **Commit if anything is valid.** If at least one staged path is a real
   change to a designated target, commit it with a `<type>: <what>` message

4. **If nothing is committable, report blocked.** Emit
   `outcome: blocked` with a `concrete_next_action` that names the exact
   failing path, the exact error, and the concrete fix the next cycle should
   make. A vague "finish the skill" handoff is not useful.
5. **Never bypass the gate.** Do not touch forbidden paths (`state/`,

# handle_loop_breaker

When the tool executor returns a loop-breaker safety alert, or when you are
about to submit a tool call whose inputs are identical to a call that already
produced the same output, **halt the repetition and transition strategy in the
same turn**. A deterministic command with unchanged inputs cannot produce a
different result; re-running it is pure waste, and the loop-breaker warning is
the harness's explicit signal that the current approach is stuck.

This skill is the executable form of `lessons/errors/ERR-2026-09-06-001.md`
(loop breaker warnings ignored — subagent re-ran the same failing test command
repeatedly) and [Lesson LESS-REF-62ca5a6de51a-530e] (change strategy
immediately rather than re-submitting the identical tool call). It addresses
the repetitive YAML-inspection failure in cycle-aaee51e6d8bb, where the agent
re-issued the same `grep`/`read` sweep against the same file until the safety
breaker stopped it.

## Recognition signals

Treat any of these as a hard stop on the current command stream:

| # | Signal | What it means |
|---|---|---|
| 1 | Tool executor returns a loop-breaker / safety-stop alert | The harness has already detected repetition; you are past the point of no return for the current approach. |
| 2 | You are about to submit a tool call whose command string is byte-identical to one you already ran this cycle | Deterministic re-run; guaranteed same output. |
| 3 | Two consecutive calls returned byte-identical output (e.g. the same empty `grep`, the same `git log` window) | The approach is not converging; a third identical call will not converge either. |
| 4 | You have re-read the same file region (same path, same offset/limit) more than once without acting on it | Reading is not progressing; the next read must change the window or the question. |

Signal 1 is the strongest: it is an explicit harness verdict. Signals 2–4 are
self-detection and must be caught **before** the call is submitted, not after
the breaker fires.

## Concrete trigger thresholds

The signals above are qualitative; the thresholds below make them
machine-checkable so you can decide in one glance whether the breaker has
fired. Count occurrences **within the current cycle** only (a new cycle
legitimately re-inspects a target — see "When NOT to use").

| Trigger | Threshold | Action |
|---|---|---|
| T1 — identical command string | 2nd submission of a byte-identical command this cycle | Halt before submitting; apply the transition procedure. |
| T2 — identical output | 2 consecutive calls returning byte-identical output | Halt; the approach is not converging. |
| T3 — same file region re-read | 2nd read of the same path with the same offset/limit window | Halt; the next read must change the window or the question. |
| T4 — empty-result sweep | 3 consecutive empty results from the same search pattern against the same path | Halt; the key/pattern is not present under that spelling. |
| T5 — no-progress window | 3 consecutive tool calls that produced no new information (no new file read, no edit, no test result, no commit) | Halt; you are spinning. Force a strategy-class change. |
| T6 — harness alert | Any loop-breaker / safety-stop alert from the tool executor | Immediate hard stop; the very next call must differ from the one that triggered it. |

T6 is the only trigger that is an external verdict; T1–T5 are self-detection
and must be caught **before** the call is submitted. If you are unsure whether
a threshold has been met, treat it as met — a false positive costs one
diverted call, a false negative costs a full loop.

## Transition procedure (execute in order, same turn)

1. **Halt.** Do not submit the next identical call. If a loop-breaker alert
   just arrived, the very next tool call must differ from the one that
   triggered it.

2. **Name the stuck input.** In one sentence, state which command/file/region
   is repeating and what output it produced. This forces you to see the
   repetition explicitly instead of treating it as a transient hiccup.

3. **Change at least one input.** Before any re-run, alter one of:
   - the **target path** (a different file, a different directory),
   - the **arguments** (different flags, a different regex, a different
     offset/limit window),
   - the **runner** (e.g. `grep` → `read_file`, `unittest` → `pytest`, or a
     single-file read instead of a sweep),
   - the **hypothesis** (re-read the prior output and the relevant source to
     form a new explanation for why it failed, then act on that explanation).

   Changing zero inputs is the failure mode this skill exists to prevent.

4. **Transition to a different strategy class.** If the repeated call was a
   search, switch to a direct read of the full file. If it was a read, switch
   to an edit or a test. If it was a test, switch to reading the failing
   source. The strategy class must change, not just the parameters.

5. **Act, don't re-diagnose.** Per the execution protocol, once you have a new
   hypothesis, proceed to the file edit or test in the same session. Do not
   end the turn after re-diagnosis without an edit, a test, or a commit.

## Tool diversion guidelines

When a specific tool is the one looping, divert to a concrete alternative
rather than re-running it with tweaked parameters. The diversion must change
the **strategy class** (search → read, read → edit, test → source-read), not
just the arguments.

| Looping tool / pattern | Divert to | Why it breaks the loop |
|---|---|---|
| `grep` / `batch-grep` returning empty repeatedly | `read_file` on the full target file | You see the actual key names / structure instead of guessing the pattern. |
| `read_file` on the same region repeatedly | `edit_file` or a targeted `exec` test | Reading is not progressing; act on what you already have. |
| `exec` test command failing identically | `read_file` on the failing source file | The test output is not new information; the source is. |
| `exec` shell command with identical output | A different runner or a different target path | Same inputs → same output; change the input class. |
| `git log` / `git show` on the same path repeatedly | `read_file` on the file, or `grep` for the change marker | History is not converging; inspect the artifact directly. |
| `list_dir` on the same directory repeatedly | `read_file` on a specific file you already know exists | You are re-exploring instead of acting. |
| Any tool called 3× with no new information | A **different strategy class** (not a parameter tweak) | Parameter tweaks within the same class are the failure mode this skill prevents. |

The rule of thumb: if the diverted call is still recognizably "the same kind
of call" as the one that looped, you have not diverted — you have re-run.
Change the class, not just the flags.

## Recovery validation

After you have diverted, confirm the loop is actually broken before resuming
normal work. A diversion that produces the same output as the looped call has
not broken the loop; it has only renamed it.

1. **Output differs.** The diverted call's output must differ from the
   looped call's output in at least one meaningful way (different content,
   different exit code, different file touched). If it is byte-identical, the
   diversion failed — apply the transition procedure again with a different
   strategy class.
2. **New information gained.** The diverted call must have produced at least
   one piece of information you did not have before (a new key name, a new
   error line, a new file region, a passing/failing test result). If it
   produced nothing new, you are still spinning.
3. **Progress toward the goal.** The diverted call must move the cycle one
   step closer to a commit (a new edit, a new test result, a new hypothesis
   that is testable). If it does not, you have diverted into a different
   spin, not out of the loop.
4. **No immediate re-loop.** After the diverted call, the next call must not
   be identical to either the original looped call or the diverted call. If
   you find yourself about to re-submit either, halt and re-apply the
   transition procedure.

If all four checks pass, the loop is broken and you may resume normal work.
If any check fails, the loop is not broken — treat the diverted call as the
new "stuck input" and re-apply the transition procedure from step 1.

## Worked example (cycle-aaee51e6d8bb pattern)

Stuck pattern: `grep -n "pattern" state/feeds/x.yaml` returned empty three
times in a row.

- **Wrong:** run the same `grep` a fourth time "to be sure".
- **Right (this skill):**
  1. Halt — the third empty result is signal 3.
  2. Name it: "grep for `pattern` in `state/feeds/x.yaml` returned empty 3x;
     the key is not present under that spelling."
  3. Change an input: read the file directly
     (`read_file state/feeds/x.yaml`) to see the actual key names, or grep for
     a broader stem (`grep -n "pat" ...`).
  4. Transition class: search → direct read.
  5. Act: edit the code to use the real key, or record the finding and move on.

## Anti-patterns (each costs a full iteration and real wall-clock time)

- Re-submitting the identical command after a loop-breaker alert.
- Treating a repeated identical output as a "transient hiccup" and retrying
  verbatim.
- Re-reading the same file region with the same offset/limit "to double-check".
- Running `git log` / `git show` on the same path repeatedly after empty
  output (see the recent-reflection note on 5 identical `git log` calls).
- Ending the turn after re-diagnosis without an edit, test, or commit.

## When to use

- The tool executor returned a loop-breaker / safety-stop alert.
- You are about to submit a tool call identical to one already run this cycle.
- Two consecutive calls returned byte-identical output.
- You have re-read the same file region more than once without acting.

## When NOT to use

- The calls are genuinely different (different path, arguments, or window) and
  merely look similar — no transition is required; continue.
- A single empty result with no prior identical call — that is normal
  exploration, not a loop; form a hypothesis and proceed.
- The repetition is across **different** cycles (a new cycle legitimately
  re-inspects a target); this skill governs repetition **within** one cycle's
  command stream.

# incremental_script_refactoring_under_step_limits

A bounded procedure for refactoring a `scripts/*.py` file in **small,
independently-verifiable increments**, running the **narrowest covering test
after each increment**, so the cycle never exhausts its step budget (80 tool
iterations) in the middle of a large, unverified rewrite.

On the eeepc host (i386, 2 GB RAM, Python 3.11) a large multi-hunk refactor
is expensive: each `edit_file` is a full iteration, each verification run is a
full iteration, and a single unbounded test sweep can consume the remaining
budget. The failure mode this skill prevents is the **all-or-nothing
refactor**: the agent spends 30 iterations editing, 10 verifying, discovers a
broken assumption, and has no budget left to fix or commit anything.

Use this skill whenever a cycle's task is to *refactor* (restructure, split,
rename, or reorganize) an existing script rather than add a small new feature.
It complements the [multi-script-refactor](multi-script-refactor/SKILL.md)
skill (which batches edits across *several* scripts atomically) and the
[run_targeted_tests_to_avoid_timeouts](run_targeted_tests_to_avoid_timeouts.md)
skill (which scopes the test run); this skill focuses on the *incremental
pacing* and *early-test* discipline that keeps a single-script refactor
within the step budget.

## Why all-or-nothing refactors fail

- **No intermediate checkpoint.** A 20-hunk rewrite has no point at which the
  code is known-good. If hunk 14 breaks an assumption, hunks 1-13 are
  stranded: the agent must either revert everything or spend the remaining
  budget debugging a half-finished state.
- **Late test feedback.** Running the covering test only after *all* edits
  means the first failure signal arrives at iteration 40+, leaving little
  budget to fix it.
- **Context bloat.** Holding a large uncommitted diff in mind across many
  iterations increases the chance of a later edit conflicting with an earlier
  one, forcing a re-read and re-edit.

## Step 0 — Plan the increments before the first edit

Before touching the file, decompose the refactor into **2-5 increments**,
each of which:

1. Leaves the script **importable and passing its covering test** on its own.
2. Is small enough to be a single `edit_file` (or at most two) call.
3. Has a **narrow test** that can verify it in isolation (a single test
   function or a `-k` keyword subset, not the whole file).

Write the plan as a short list in your working notes (not a file). Example for
splitting a 400-line script into two modules:

```
Increment 1: extract helper functions into scripts/_helpers.py (pure move, no logic change)
  -> verify: python3 -m pytest tests/test_<name>.py -q -k "helper"
Increment 2: update <name>.py to import from _helpers, remove the moved code
  -> verify: python3 -m pytest tests/test_<name>.py -q
Increment 3: (optional) rename the public entry point and update its test
  -> verify: python3 -m pytest tests/test_<name>.py -q -k "entry"
```

If you cannot name a test that verifies an increment in isolation, the
increment is too large — split it further.

### Atomic step slicing rules

An increment is **atomic** only if it satisfies all of the following. If any
rule fails, split the increment before applying it:

1. **Single concern.** The increment changes exactly one thing (one extraction,
   one rename, one import swap). "Move the helper *and* update its callers"
   is two increments unless the move is impossible without the caller update —
   in which case they are one increment by definition.
2. **One or two `edit_file` calls.** If the increment needs three or more
   edits, it is not atomic. Split at a natural seam (e.g. move the code first,
   then update the imports).
3. **One narrow test command.** The verification must be a single pytest
   invocation (one file, optionally with `-k`). If you need two different
   test commands to prove the increment, the increment covers two concerns.
4. **Reversible in one step.** You must be able to undo the increment with a
   single `git revert <commit>` or one inverse `edit_file`. If undoing it
   requires re-doing other work, the increment is entangled — split it.
5. **No cross-file coupling.** The increment touches at most the target
   script and its test file (plus one new module if extracting). If it also
   requires editing a third file, defer that file to a later increment.

A good rule of thumb: if you cannot describe the increment in one sentence
that names exactly one change and one test, it is not atomic.

## Step 1 — Make the first increment and verify it immediately

Apply the first increment with `edit_file`, then **immediately** run the
narrow covering test for that increment. Do not proceed to the next increment
until this one passes.

```bash
# After increment 1 (pure extraction):
python3 -m pytest tests/test_<name>.py -q -k "helper" 2>&1 | tail -n 20
```

Rules:

1. **Verify after every increment, not after all of them.** The test run is
   the checkpoint that makes the next increment safe.
2. **Use the narrowest test that covers the increment.** A `-k` keyword or a
   single node id is faster and gives a cleaner signal than the whole file.
3. **Cap the output** with `tail -n 20` so the verification does not blow the
   context budget.
4. **If the increment fails, fix it now.** You have a small, isolated diff to
   debug, not a 20-hunk mess. This is the entire point of the discipline.

## Step 2 — Commit each verified increment

After each increment passes its narrow test, **commit it** on the cycle
branch. This gives the harness (and the next cycle, if this one runs out of
budget) a concrete, known-good artifact to build on.

```bash
git add scripts/<name>.py scripts/_helpers.py
git commit -m "refactor(<name>): extract helpers into _helpers.py"
```

Rules:

1. **Stage only the files the increment touched.** Never `git add -A`.
2. **One commit per increment** is ideal; if two increments are tightly
   coupled and cannot be verified independently, commit them together.
3. **A committed increment is a checkpoint.** If a later increment fails and
   the budget is nearly exhausted, the cycle ends with a valid partial
   refactor already committed — not a stranded half-finished diff.

## Step 3 — Continue until the refactor is complete or the budget is low

Repeat Steps 1-2 for each remaining increment. Track your iteration count
against the 80-iteration budget:

| Checkpoint | Rule |
|---|---|
| ≤ 16 | Plan done, first increment applied and verified. |
| ≤ 30 | At least two increments committed. |
| ≤ 50 | If not all increments are done, stop planning new ones; finish the current one and commit. |
| ≤ 60 | If the refactor is not complete, commit the last verified increment and report the remaining work in `concrete_next_action`. |

The key rule: **never start an increment you cannot finish and verify within
the remaining budget.** If you are at iteration 55 and the next increment
needs 15 iterations, do not start it — commit what you have and hand off.

### Turn-reserve allocation thresholds

Before starting each increment, compute the **turn reserve**: the iterations
you must keep in hand to (a) verify the increment, (b) commit it, and (c)
emit the final structured response. The reserve is not optional slack — it is
the cost of finishing cleanly.

| Phase (iteration) | Minimum reserve to hold | What the reserve must cover |
|---|---|---|
| Planning (≤ 16) | 20 | Full verification + commit + final response for the *last* increment. |
| Mid-refactor (17–50) | 12 | One narrow test run, one commit, one final response. |
| Late (51–60) | 8 | One test run, one commit, one final response — no new increments. |
| Terminal (61–80) | 4 | Commit the last verified increment and emit the final response only. |

Rules:

1. **Reserve is computed per increment, not once.** After each commit,
   recompute: `reserve_needed = 4 (verify) + 2 (commit) + 2 (final response)
   = 8` at minimum. If `iterations_used + reserve_needed > 80`, stop starting
   new increments.
2. **The reserve shrinks as you go.** Early on you can afford a 20-iteration
   reserve (room for a failed increment + fix + re-verify). Late in the cycle
   the reserve is only 4: commit and respond. Do not start an increment whose
   expected cost exceeds the current reserve.
3. **A failed verification consumes reserve.** If a narrow test fails, the
   fix + re-verify costs 4–6 extra iterations. If that would push you past the
   reserve, do not attempt the fix — roll back the increment (see the
   rollback protocol below) and hand off.
4. **Never spend the reserve on planning.** If you are at iteration 65 and
   still planning increment 4, stop planning. The reserve exists to finish,
   not to start.

## Step 4 — Final verification and handoff

When all increments are committed, run the **full covering test file** once to
confirm the refactor as a whole is sound:

```bash
python3 -m pytest tests/test_<name>.py -q 2>&1 | tail -n 40
```

If it passes, the cycle is complete: emit the structured final response.
If it fails on something outside your target scope, note it in
`concrete_next_action` and do not fix it in this cycle.

If the budget ran out mid-refactor, the final response should:

- Report `outcome: completed` (the committed increments are real, verified

## Verification rollback protocol

When a narrow test fails after an increment is applied, follow this protocol
instead of ad-hoc debugging. The goal is to restore a known-good state within
the turn reserve, not to fix the failure at any cost.

### Decision tree

```
Test fails after increment N
  |
  +-- Can you identify the cause in <= 2 iterations (read the diff, check
  |   the error)?
  |     YES -> Apply a minimal fix (1 edit_file), re-run the narrow test.
  |            If it passes: commit and continue.
  |            If it fails again: ROLL BACK (below). Do not attempt a second
  |            fix — you have spent the reserve.
  |     NO  -> ROLL BACK immediately. Do not spend iterations guessing.
  |
  +-- ROLL BACK:
        1. git revert --no-edit HEAD   (if the increment was committed)
           OR
           git checkout -- scripts/<name>.py   (if uncommitted)
        2. Re-run the narrow test to confirm the known-good state passes.
        3. If the increment was committed, the revert is itself a commit —
           the branch history shows the attempt and its undo. This is fine;
           the harness integrates the net state.
        4. Stop. Do not start the next increment. Emit the final response
           with outcome: completed (if earlier increments are committed) or
           blocked (if no increment survived).
```

### Rollback rules

1. **One fix attempt maximum.** After a failed increment, you get exactly one
   minimal fix + re-verify. A second failure means the increment's premise
   was wrong — rolling back is cheaper than debugging a broken assumption
   with no budget.
2. **Rollback is a commit, not a loss.** A reverted increment leaves the
   branch in a known-good state with a clear history. The next cycle can
   re-attempt the increment with the failure evidence in
   `concrete_next_action`.
3. **Never roll back more than one increment.** If increment N fails and you
   roll it back, do not also roll back increment N-1. Increment N-1 passed
   its test and is a valid checkpoint. Rolling back multiple increments
   destroys verified work and wastes the reserve.
4. **Document the failure.** In `concrete_next_action`, state: which
   increment failed, the exact test error (first 3 lines), and the specific
   fix the next cycle should try. A vague "the test failed" handoff is not
   useful.
5. **Rollback costs 2–3 iterations** (revert + verify + respond). If your
   remaining budget is less than 3, do not roll back — leave the failed
   increment uncommitted (it is not in the branch) and emit the final
   response with `outcome: blocked`.

```bash
grep -n "<keyword>" memory/HISTORY.md | tail -20
```

# posix_background_execution_in_sh

Run a command in the background so it survives the calling shell exiting,
using only POSIX `sh` constructs. The canonical pattern is:

```sh
nohup cmd arg1 arg2 >/dev/null 2>&1 &
```

This skill exists because the most common "detach" idiom, `disown`, is a
bash/zsh builtin and is **not** available under `/bin/sh` (dash on Debian).
A script that runs `cmd & disown` under `sh` fails with
`disown: not found`, and the background job may be killed when the parent
shell exits.

## Why `disown` fails under /bin/sh

- `disown` is a bash/zsh builtin that removes a job from the shell's job
  table so it is not sent SIGHUP on shell exit. POSIX `sh` (dash) has no
  `disown` builtin and no job-control table to consult.
- Under `sh`, a plain `cmd &` job is still a child of the shell. When the
  shell exits, the child is reparented to init (PID 1) and normally keeps
  running — but it still receives SIGHUP if the controlling terminal is
  closed, and its stdout/stderr are still attached to the terminal, which
  can block or interleave output.
- `nohup` (POSIX) makes the child immune to SIGHUP; the redirections detach
  its file descriptors from the terminal. Together they give the same
  practical effect as `disown` without any non-standard builtin.

## The standard patterns

### 1. Fire-and-forget (no output needed)

```sh
nohup cmd arg1 arg2 >/dev/null 2>&1 &
```

- `nohup` — ignore SIGHUP.
- `>/dev/null 2>&1` — detach stdout and stderr from the terminal.
- `&` — run in the background.

### 2. Keep a log (recommended for anything you may need to debug)

```sh
nohup cmd arg1 arg2 >>/var/log/myapp.log 2>&1 &
```

Prefer an absolute log path under a dedicated application directory (e.g.
`/var/lib/eeepc-agent/...`), never a personal home directory, so the log
survives user changes and stays writable by the service account.

### 3. Capture the PID for later management

```sh
nohup cmd arg1 arg2 >/dev/null 2>&1 &
echo $! > /var/run/myapp.pid
```

`$!` is the PID of the most recent background job. Store it in a pidfile
under a dedicated runtime directory so a later script can stop the process
with `kill "$(cat /var/run/myapp.pid)"`.

### 4. Detach from the controlling terminal entirely (full daemon)

When the process must not be tied to any terminal at all (e.g. it opens
its own log or socket), wrap it so stdin is also closed:

```sh
nohup cmd arg1 arg2 </dev/null >/dev/null 2>&1 &
```

For a true double-fork daemon (reparent to init, new session), use a small
POSIX helper rather than bashisms:

```sh
(
  nohup cmd arg1 arg2 </dev/null >/dev/null 2>&1 &
  exit 0
)
```

The subshell exits immediately, so the grandchild is reparented to init
and is fully detached from the caller's process group.

## What NOT to do under /bin/sh

| Bashism | Why it fails under sh | POSIX replacement |
|---|---|---|
| `cmd & disown` | `disown` is not a sh builtin | `nohup cmd >/dev/null 2>&1 &` |
| `cmd & disown -h` | same | same |
| `setsid cmd &` | `setsid` is not POSIX (though present on Linux) | subshell + `nohup ... &` |
| `cmd &> /dev/null` | `&>` is a bash/zsh redirection, not POSIX | `>/dev/null 2>&1` |
| `cmd 2>&1 &> /dev/null` | same | `>/dev/null 2>&1` |

## Verification

After launching, confirm the process is running and detached:

```sh
# Confirm it is alive and its parent is init (PID 1) or a non-shell.
ps -o pid,ppid,cmd -p "$(cat /var/run/myapp.pid)" 2>/dev/null
```

A `PPID` of `1` (or a non-shell supervisor) confirms the process has been
reparented and will survive the launching shell's exit.

## When to use

- Launching a long-running helper from a `sh` script or a harness cycle.
- Starting a background worker whose lifetime must outlive the caller.
- Any context where the shell is `/bin/sh` (dash) and `disown` is
  unavailable.

## When NOT to use

- If the process is managed by systemd, prefer a unit file over a manual
  `nohup` launch; the harness's `systemd/` tree is the control plane and is
  not a mutation surface for this skill.
- If you only need the command to run in the background for the lifetime of
  the current shell (no detach needed), a plain `cmd &` is sufficient and
  `nohup` is unnecessary.

# recursive_unittest_testsuite_traversal

Flatten nested `unittest.TestSuite` hierarchies into a flat list of leaf
`TestCase` instances during test discovery. Use this when a test runner
groups discovered tests by source module (e.g. to build a per-module target
map) and the suite returned by `TestLoader.discover()` contains nested
sub-suites rather than only direct `TestCase` children.

## Why this is needed

`unittest.TestLoader.discover()` returns a `TestSuite` whose children are
themselves `TestSuite` objects (one per discovered module), not bare
`TestCase` instances. A naive two-level loop:

```python
for test in suite:
    for case in test:
        ...
```

works only when every child is a flat suite of `TestCase` objects. When a
module defines a `load_tests` protocol that returns a nested suite, or when
the loader wraps results in an extra layer, the inner iteration yields
`TestSuite` objects instead of `TestCase` instances. Calling
`type(case).__module__` on a `TestSuite` returns `unittest.suite`, so the
module map is keyed on the wrong module and the real test modules are
missing — producing an empty or incorrect module map (as seen in
cycle-bbac694036ae).

## The pattern

Replace the fixed-depth loop with a recursive (or iterative) traversal that
descends into every `TestSuite` child until it reaches `TestCase` leaves:

```python
import unittest

def flatten_suite(suite: unittest.TestSuite) -> list[unittest.TestCase]:
    """Recursively flatten a TestSuite into its leaf TestCase instances."""
    leaves: list[unittest.TestCase] = []
    for child in suite:
        if isinstance(child, unittest.TestSuite):
            leaves.extend(flatten_suite(child))
        else:
            leaves.append(child)
    return leaves
```

Then group by the leaf's defining module:

```python
by_module: dict[str, int] = {}
for case in flatten_suite(suite):
    module = type(case).__module__
    by_module[module] = by_module.get(module, 0) + 1
```

## Iterative variant (avoids recursion depth limits)

For very deep hierarchies, use an explicit stack instead of recursion:

```python
def flatten_suite_iterative(suite: unittest.TestSuite) -> list[unittest.TestCase]:
    leaves: list[unittest.TestCase] = []
    stack = [suite]
    while stack:
        current = stack.pop()
        for child in current:
            if isinstance(child, unittest.TestSuite):
                stack.append(child)
            else:
                leaves.append(child)
    return leaves
```

Both variants are deterministic in count (order may differ between
recursive and iterative; sort the result if order matters).

## Applying to run_all_tests.py

In `scripts/run_all_tests.py`, `discover_unittest_targets()` builds a
per-module target map from the suite returned by
`unittest.TestLoader.discover()`. The grouping loop must use the recursive
traversal above so that modules whose tests are wrapped in nested suites
are still counted. Without it, those modules are absent from the map and
the `unittest` suite silently skips them.

1. Create a temporary test module that defines a `load_tests` protocol
   returning a nested `TestSuite`:

   ```python
       def test_a(self):
           self.assertTrue(True)

   def load_tests(loader, tests, pattern):
       inner = loader.loadTestsFromTestCase(TestInner)
       outer = unittest.TestSuite()
       outer.addTests([inner])  # nested one level deeper
       return outer
   ```
2. Run discovery over the temp directory and assert the module appears in
   the flattened map with the correct test count.
3. Run the existing `run_all_tests.py` self-tests to confirm no regression:
   ```bash
   python3 scripts/run_all_tests.py --test 2>&1 | tail -20
   ```

## Constraints

- The traversal must handle an empty suite (return an empty list).
- Do not assume a fixed nesting depth; recurse until `TestCase` leaves.
- Keep the traversal pure (no I/O) so it is testable in isolation.
- On the eeepc host, bound any test output through `tail -N`.

## When to use

- Any runner that iterates a discovered suite and needs leaf `TestCase`
  instances (for counting, grouping, or selective execution).
- Not needed when the suite is known to be exactly two levels deep and no

# Target git log history inspection (single-file fixes)

## Target git log history inspection (single-file fixes)
<!-- prompt-fit: droppable -->

For single-file fix tasks, one bounded `git log` pass over the target file
before editing reveals whether a previous cycle already applied the integrity,
formatting, or content fix the task asks for — avoiding redundant rework:

1. **One pass, bounded.** Run `git log --oneline -5 -- <target>` (or
   `git log -1 -p -- <target>` to see the last change's diff) as part of the
   turn-2 redundancy check. This is the one targeted history scan the skip
   protocol permits; it is not an auxiliary "double-check" of a proven skip.
2. **Read the diff, not the whole history.** If the last commit's patch
   already contains the fix (e.g. the integrity/formatting change the task
   names), stop and report `outcome: skipped` with the commit hash as
   evidence. Do not page through older commits.
3. **If the fix is absent, proceed to edit.** The log pass is a gate, not a
   reading list: once you have confirmed the target's last change does not
   already satisfy the task, move to the first `edit_file` on the target
   without further history inspection.

## Invocation triggers (when to run this skill)

Run the single-file history pass when **all** of the following hold:

1. **The task names exactly one target path** (a script, skill, lesson, doc,
   or test file) and the change is a fix or extension to that file — not a
   new file and not a multi-file refactor.
2. **The target already exists** in the working tree. If the path is absent,
   the work is not done; skip the history pass and go straight to
   `write_file`.
3. **The task is a "fix" or "extend" verb** (fix, repair, extend, add,
   improve, normalize) on an existing file. Pure greenfield creation tasks
   have no history to inspect.

Do **not** run this pass for: multi-file tasks (use a per-file pass only if a
specific file's history is in question), tasks where the target is a new
file, or after a proven skip (the pass is the skip check, not a re-check).

## Single-file patch extraction workflows

Each workflow is one bounded `exec` call. Substitute `<target>` with the
designated path. Keep output bounded; never page through full history.

### 1. Last-change patch (the default skip check)

```sh
git log -1 -p -- <target>
```

Shows the most recent commit that touched the file plus its full diff.
Decision rule:

- **Patch already contains the named fix** (the exact header, flag, or
  content the task asks for) → stop, report `outcome: skipped`, cite the
  commit hash from the header line.
- **Patch is unrelated or partial** → proceed to edit; do not inspect older
  commits.

### 2. Bounded recent history (when the last change is ambiguous)

```sh
git log --oneline -5 -- <target>
```

Lists the five most recent commits touching the file, one line each. Use this
only when workflow 1's single patch is inconclusive (e.g. the last commit
touched the file for an unrelated reason). Pick at most **one** of those
hashes and inspect it with workflow 3. Do not loop over all five.

### 3. Extract a specific commit's patch by hash

```sh
git show -p --stat <hash> -- <target>
```

`--stat` gives a one-line file summary; `-p` gives the diff restricted to
`<target>`. Use this to confirm whether a specific historical commit already
applied the fix. If it did, report `outcome: skipped` with that hash.

### 4. Detect whether the file was ever modified (new-file guard)

```sh
git log --oneline -- <target> | head -1
```

Empty output means the file has no history (untracked or never committed):
the task cannot already be done, so skip the history pass entirely and edit.

### 5. Compare working tree against the last commit (uncommitted-change check)

```sh
git diff -- <target>
```

Shows uncommitted local changes to the file. If the working tree already
contains the fix (e.g. a prior cycle edited but did not commit), the task is
effectively done: stage and commit the existing change rather than
re-implementing it, and note this in `concrete_next_action`.

## Bounding rules

- **At most two `exec` calls** for the whole history pass (one default check
  plus at most one follow-up). A third history call is a budget leak.
- **Always pass the path filter** (`-- <target>`). Unfiltered `git log`
  dumps the whole repository history and burns the turn budget.
- **Never page** (`git log -p` without `-1`, `git log --all`, `git reflog`)
  in a single-file fix cycle.
- **Stop at the first conclusive answer.** The pass exists to answer one
  question — "is the fix already applied?" — not to build a narrative of the
  file's history.

## Handoff to editing

Once the pass concludes the fix is absent, the next tool call is the first
`edit_file`/`write_file` on `<target>`. Do not re-read the file's history,
lessons, or reflections at that point; the pass is the gate, and the edit is
the work.
